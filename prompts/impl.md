# 단계: 구현

기능: $FEATURE

## 출력 (이 파일 하나만 쓴다)
`$WORK/IMPL.md`

## 입력 (읽기만, 절대 수정 금지)
- `$WORK/DESIGN.md` — 이 설계를 그대로 구현한다
- `$WORK/FAIL_LOG.md` — 비어있지 않다면 이전 시도가 실패한 것이다. 같은 실패를 반복하지 마라.
- `$ROOT/HANDOFF.json` — 배경 참고용. 설계와 충돌하면 설계가 우선이다.

## 할 일
1. DESIGN.md 의 "변경 대상 파일 목록"대로만 수정한다.
2. 목록에 없는 파일을 건드려야 한다면 STATUS: BLOCKED.
   이건 부탁이 아니다 — 구현 직후 셸이 `git status` 와 DESIGN.md 의 ALLOWED_FILES 를 대조해서
   목록 밖 파일이 하나라도 바뀌었으면 파이프라인을 죽인다. 우회로는 없다.
3. 수정 후 `flutter analyze`를 실행하고, 실제 실행한 명령과 출력 요지를 IMPL.md에 기록한다 (통과 판정은 파이프라인이 별도로 한다).
4. 작업 요약을 `$WORK/IMPL.md` 에 쓴다.

## 이 프로젝트의 주의점
- flutter_riverpod이 3.0.0-dev.17 프리릴리스다. 정식판 API 문서와 다를 수 있으니 이 저장소의 기존 사용 패턴을 따른다.
- 이 스트림의 원칙: **사용자에게 보이는 동작은 그대로여야 한다.** 구조만 바꾸고 동작을 바꾸지 않는다. 동작이 바뀔 수밖에 없다면 설계에 그렇게 적혀 있어야 한다 — 안 적혀 있으면 STATUS: BLOCKED.
- 성공 경로(세션 시작→번역 수신→Stop)와 P0 에서 고친 실패 경로 모두 실기기 검증을 통과한 상태다. 어느 쪽도 회귀시키지 않는다.
- `test/fake-claude`, `test/run-tests.sh`, `prompts/`, `orchestrate.sh`, `advisor.sh`는 파이프라인 하네스다. 절대 건드리지 않는다.

## IMPL.md 필수 섹션
- STATUS 라인 (첫 줄)
- 실제로 수정한 파일 목록 (설계와 다르면 그 이유)
- 설계와 달라진 점 (없으면 "없음")
- 다음 단계(검증)가 알아야 할 것 (뽑아낸 순수 로직의 위치·시그니처 포함)

## 금지
- 테스트를 작성하지 않는다. 그건 다음 단계다.
- 설계를 바꾸지 않는다. 설계가 틀렸으면 BLOCKED.
